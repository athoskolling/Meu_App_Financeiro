### Objetivo

Existe o tipo `NormalizedTransaction` e a função `validateTransaction`, que devolve **todos** os problemas de uma transação, em ordem fixa, sem lançar exceção por regra de negócio e sem mutar a entrada.

### Contexto mínimo

- Os casos da T1.0 são a especificação. Se algum parecer contraditório com outro ou com a spec, **não ajuste o caso**: pare e relate.
- Valide em tempo de execução também os campos que o tipo já garante (a entrada pode vir de fonte não confiável). `amount` fracionário é `invalid_amount` e não gera `sign_mismatch`.
- A data é validada por aritmética (ano bissexto incluído), **sem `Date`**.
- `amount` é `Cents` (T1.1, já em `main`).

**Decisões minhas:**

- `accountRef` só com espaços também é `empty_account_ref` (o caso aprovado cobre `''`; o `trim` é extensão).
- `time` e `postedAt` só são validados quando presentes (`!== undefined`); presentes e não string viram `invalid_time` / `invalid_posted_at`. `postedAt` é validado como data civil `YYYY-MM-DD` (o caso aprovado só traz esse formato).
- `amount` que não é inteiro seguro (fracionário, NaN, Infinity, 2**53, string, null) é `invalid_amount`; nesse caso não há `sign_mismatch`. Zero é só aviso `zero_amount`.
- `type` desconhecido gera só `invalid_type`, sem `sign_mismatch`.
- Anos válidos: 1 em diante (ano 0000 é `invalid_date`).
- Extras de teste além da tabela: `00:00`, dia 31 em mês de 30 dias, tipos não string, ordem com todos os campos inválidos, e checagem de que o resultado tem só `code`, `field` e `severidade`.
- A ordem "`invalid_amount` antes de `sign_mismatch`" no mesmo campo é satisfeita trivialmente: os dois nunca coexistem pela regra do cartão. Não há teste que os force juntos.

**Riscos:** a validação confia em `String.prototype.trim` e em regex (sem `Intl`); `trim` do JS remove espaços Unicode como U+00A0, o que é desejado aqui. Nenhum caso da T1.0 pareceu contraditório.

**Bugs:**

- **BUG-T1.2-01 (média): `validateTransaction(null)` lança `TypeError`.**
  - Reprodução: `validateTransaction(null as unknown as NormalizedTransaction)`, ou `pnpm test tests/qa/transactions-qa.test.ts -t BUG-T1.2-01`.
  - Esperado: devolve `ValidationResult` com os problemas, sem lançar.
  - Obtido: `TypeError: Cannot read properties of null (reading 'source')`.
  - Por que é média: o cartão diz que a entrada "pode vir de fonte não confiável". Um adapter com defeito que entregue `null` derruba o lote inteiro, em vez de gerar problemas. O cartão proíbe lançar "por regra de negócio"; `null` não é regra de negócio, então o briefing do QA (não lançar) prevalece. Se o CTO decidir que entrada não-objeto é erro de programação (como fez em `assignIdentities`), o caso sai do cartão com aprovação do dono. Não cabe ao QA mudar o teste.
- **BUG-T1.2-02 (média): `validateTransaction(undefined)` lança `TypeError`.** Mesma causa e mesma reprodução com `undefined`.
- **BUG-T1.2-03 (média): um getter que lança derruba a validação.**
  - Reprodução: objeto com `Object.defineProperty(obj, 'type', { enumerable: true, get() { throw new Error() } })`, e chamar `validateTransaction(obj)`.
  - Esperado: sem lançar. Obtido: `Error: getter hostil`.
- **BUG-T1.2-04 (média): um Proxy cujo `get` lança derruba a validação.** Mesma linha de reprodução, com `new Proxy(base, { get() { throw new Error() } })`.

Sugestão para o dev (não é o QA que corrige): tratar entrada que não é objeto como objeto sem campos, e ler cada campo dentro de um `try`, ou pegar a exceção no ponto de leitura.

**Observações (não derrubam o veredito):**

- **O1 (baixa): descrição só com U+200B (espaço de largura zero) é aceita como não vazia.** `trim` do JS não remove esse caractere. A T1.0 diz "vazia ou só espaços", então a regra está correta para o texto como escrito. Vale o CTO decidir se entra em `isBlank`.
- **O2 (informativa): a regra de ordem entre `invalid_amount` e `sign_mismatch` é inalcançável.** `amount` é checado em um `if` / `else if`. `sign_mismatch` só roda quando o valor é inteiro seguro e diferente de zero; `invalid_amount` só roda quando não é. São mutuamente exclusivos por construção, e o cartão manda que fracionário não gere `sign_mismatch`. Fuzz de 2000 combinações não achou nenhum par. A cláusula é satisfeita trivialmente, sem caso que a force. Recomendação ao CTO: remover a cláusula do contrato (mudança que exige aprovação do dono, pois é o contrato da T1.0) ou registrar que é invariante vazio. Não é bug.
- **O3 (baixa): a função lê o mesmo campo mais de uma vez** (por exemplo, `type` em três pontos). Com um getter que muda de valor entre leituras, o resultado pode misturar valores. Recomendação: ler cada campo uma vez para um snapshot local.
- **O4 (informativa): ano 0000 é recusado.** É decisão do dev, descrita no relatório. Não está na ADR-0018 nem na T1.0. Sugestão: registrar na ADR ou aceitar explicitamente. Os testes do QA fixam essa decisão.
- **O5 (informativa): `time: null` e `postedAt: null` viram `invalid_time` e `invalid_posted_at`.** Só `undefined` é "ausente". Decisão razoável, fixada em teste do QA.
