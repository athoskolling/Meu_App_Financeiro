# T1.0: Casos de teste do núcleo (Money, NormalizedTransaction, identidade)

## Cartão (preenchido pelo CTO)

- **Estágio / tarefa:** E1 parte A / T1.0
- **Responsável:** CTO (escreve). O **dono aprova** antes de qualquer implementação.
- **Revisor:** não se aplica (não há código). O revisor confere nas T1.1 a T1.3 se os testes implementam estes casos ao pé da letra.
- **Depende de:** gate E0 fechado (tag `v0.0`, 15/10/2026)
- **Status:** escrito em 15/10/2026, **aguardando o "aprovo" do dono**

### Objetivo

Fixar, antes do código, o comportamento exato das três peças do núcleo. As T1.1, T1.2 e T1.3 implementam até estes casos passarem. Um caso só muda com nova aprovação do dono, registrada neste arquivo.

### Decisões que estes casos assumem

Todas estão em **ADR-0018** (aprovada pelo dono em 15/10/2026, junto com o lote de cartões). Resumo:

1. `Cents` é `number` com brand, sempre inteiro seguro. O `bigint` aparece só na borda com o banco (`fromDb`).
2. `formatBRL` não usa `Intl` e só gera espaço comum (U+0020).
3. Erro de dinheiro tem **código** e a mensagem **não repete a entrada** (logs sem valores).
4. `date` é string civil `YYYY-MM-DD`, validada por aritmética, sem `Date`.
5. `validateTransaction` devolve **todos** os problemas, em ordem fixa. Descrição vazia é **erro**; valor zero é **aviso**.
6. O texto da `baseKey` é a `description` normalizada. `merchantName` **fica fora**, porque o enriquecimento da Pluggy pode aparecer e sumir entre sincronizações e mudaria a identidade.
7. Ficam fora da `baseKey`: `status`, `type`, `postedAt`, `externalId` e `merchantName`.

### Regras gerais para os testes das três tarefas

- Os nomes dos testes descrevem a **regra**, não a implementação. Exemplo: "reimportação integral não cria linha nova".
- Nada de `Date.now()`, `new Date()` sem argumento ou `Math.random` em `domain/` nem nos testes. Data de referência, quando houver, vem por parâmetro.
- Nada de `console` em `domain/`.
- Classes de erro usam nome literal (`this.name = 'MoneyError'`), porque `this.constructor` é barrado pelo lint (ADR-0017).
- Testes ficam em `tests/domain/<módulo>/`.

## A. Money (T1.1), `domain/money/`

### Contrato

```ts
type Cents = number & { readonly __brand: 'Cents' };
type MoneyErrorCode =
  | 'empty' | 'invalid_format' | 'ambiguous_format' | 'out_of_range' | 'not_integer';
class MoneyError extends Error { readonly code: MoneyErrorCode }

cents(value: number): Cents                          // único jeito de criar Cents a partir de number
parseBRL(input: string): Cents
formatBRL(value: Cents): string
fromDb(value: string | number | bigint): Cents
add(a: Cents, b: Cents): Cents
sum(values: readonly Cents[]): Cents
negate(value: Cents): Cents
```

Todas as funções que falham lançam `MoneyError` com o `code` indicado. A `message` é útil ("formato americano não é aceito; use 1.234,56"), mas **nunca contém a entrada** (teste: para cada caso de erro, `message` não inclui os dígitos da entrada).

### A.1 `cents`

| Entrada | Esperado |
|---|---|
| `1230` | `1230` |
| `-1230` | `-1230` |
| `0` | `0` |
| `-0` | `0`, e `Object.is(resultado, 0)` é verdadeiro |
| `Number.MAX_SAFE_INTEGER` | aceito |
| `-Number.MAX_SAFE_INTEGER` | aceito |
| `1.5` | `not_integer` |
| `NaN`, `Infinity`, `-Infinity` | `not_integer` |
| `2 ** 53` | `out_of_range` |

Teste de tipo (com `// @ts-expect-error`, verificado pelo `pnpm typecheck`): `const x: Cents = 5;` não compila.

### A.2 `parseBRL`

Gramática aceita, depois de tirar espaços das pontas (inclusive U+00A0 e U+202F):

- sinal opcional `-` ou `+`, com ou sem espaço depois, **antes ou depois** de `R$`;
- `R$` opcional, com ou sem espaço depois (espaço comum, U+00A0 ou U+202F);
- **ou** o valor inteiro entre parênteses, que significa negativo;
- parte inteira: só dígitos, **ou** grupos de milhar com `.` (primeiro grupo de 1 a 3 dígitos, os demais com exatamente 3);
- vírgula decimal opcional, seguida de 1 ou 2 dígitos.

| Entrada | Esperado |
|---|---|
| `"1.234,56"` | `123456` |
| `"R$ 12,30"` | `1230` |
| `"R$12,30"` | `1230` |
| `"R$ 12,30"` (espaço não separável) | `1230` |
| `"  R$ 12,30  "` | `1230` |
| `"-R$ 12,30"` | `-1230` |
| `"- R$ 12,30"` | `-1230` |
| `"R$ -12,30"` | `-1230` |
| `"+R$ 12,30"` | `1230` |
| `"(12,30)"` | `-1230` |
| `"(R$ 12,30)"` | `-1230` |
| `"12"` | `1200` |
| `"12,3"` | `1230` |
| `"0,01"` | `1` |
| `"0,5"` | `50` |
| `"1234,56"` | `123456` |
| `"1.234"` | `123400` (ponto é milhar em BRL) |
| `"12.345.678,90"` | `1234567890` |
| `"-0,00"` | `0`, e `Object.is(resultado, 0)` é verdadeiro |
| `"90.071.992.547.409,91"` | `9007199254740991` |
| `"90.071.992.547.409,92"` | `out_of_range` |
| `"1,234.56"`, `"R$ 1,234.56"`, `"12,30.5"` | `ambiguous_format` (tem `,` e `.`, e o último separador é `.`: cara de formato americano) |
| `"1.234.56"` | `invalid_format` (não tem vírgula; grupo final com 2 dígitos) |
| `""`, `"   "` | `empty` |
| `"abc"`, `"R$"`, `"12,345"`, `",50"`, `"1.23"`, `"1234.567,00"`, `"12,"`, `"--12"`, `"-(12,30)"`, `"12 30"`, `"1e3"` | `invalid_format` |

Regra de implementação, testada pelos casos de faixa: os dígitos viram centavos sem passar por `parseFloat` nem por multiplicação de número quebrado. A faixa é checada antes da conversão.

### A.3 `formatBRL`

| Entrada | Esperado |
|---|---|
| `0` | `"R$ 0,00"` |
| `1` | `"R$ 0,01"` |
| `-1` | `"-R$ 0,01"` |
| `1230` | `"R$ 12,30"` |
| `-1230` | `"-R$ 12,30"` |
| `123456` | `"R$ 1.234,56"` |
| `123456789` | `"R$ 1.234.567,89"` |
| `Number.MAX_SAFE_INTEGER` | `"R$ 90.071.992.547.409,91"` |
| `1.5 as Cents` | `not_integer` |

- Nenhuma saída contém U+00A0 nem U+202F. Teste com regex sobre todas as saídas acima.
- **Ida e volta:** `parseBRL(formatBRL(x)) === x` para `0, 1, -1, 99, 100, 101, 123456, -123456, Number.MAX_SAFE_INTEGER, -Number.MAX_SAFE_INTEGER`.

## B. NormalizedTransaction (T1.2), `domain/transactions/`

### Contrato

O tipo é o do roteiro (Tarefa 2), sem mudança. A validação:

```ts
type ProblemCode =
  | 'invalid_source' | 'empty_account_ref' | 'invalid_date' | 'invalid_time'
  | 'invalid_posted_at' | 'empty_description' | 'invalid_amount' | 'zero_amount'
  | 'sign_mismatch' | 'invalid_currency' | 'invalid_type' | 'invalid_status';

interface Problem { code: ProblemCode; field: keyof NormalizedTransaction; severity: 'error' | 'warning' }
interface ValidationResult { ok: boolean; problems: Problem[] }   // ok = nenhum problema de severidade 'error'

validateTransaction(t: NormalizedTransaction): ValidationResult
```

- Não lança exceção por regra de negócio. A entrada pode vir de fonte não confiável, então a função confere em tempo de execução também os campos que o tipo já garante.
- **Ordem dos problemas:** a ordem dos campos no contrato (`source`, `accountRef`, `date`, `time`, `postedAt`, `description`, `amount`, `currency`, `type`, `status`). Dois problemas no mesmo campo saem em ordem fixa: `invalid_amount` e depois `sign_mismatch`.
- Não muta a entrada (teste com `Object.freeze`).

### Casos

Base válida usada nos casos (cada caso muda só o que diz): `{ source: 'manual', accountRef: 'conta-1', date: '2026-10-06', description: 'Padaria Exemplo', amount: -830, currency: 'BRL', type: 'expense', status: 'posted' }`.

|---|---|

| `expense` com `+830` | `sign_mismatch` (erro, campo `amount`) |

| `credit_card_purchase` com `+830` | `sign_mismatch` |
| `income` com `+500000` | ok |
| `income` com `-500000` | `sign_mismatch` |

| `transfer` com `+830` e com `-830` | ok nos dois |

## C. Identidade e dedup (T1.3), `domain/transactions/identity.ts`

### Contrato

```ts
type Hash = (input: string) => string;   // injetado: domain/ não importa node:crypto
type Mode = 'complete' | 'incremental';

normalizeText(s: string): string
baseKeyInput(t: NormalizedTransaction): string            // texto canônico, antes do hash
baseKey(t: NormalizedTransaction, hash: Hash): string     // hash(baseKeyInput(t))
identityKey(baseKey: string, occurrence: number, hash: Hash): string
assignIdentities(
  batch: readonly NormalizedTransaction[],
  existingCounts: ReadonlyMap<string, number>,   // baseKey -> linhas já gravadas
  mode: Mode,
  hash: Hash,
): Array<{ tx: NormalizedTransaction; baseKey: string; occurrence: number; identityKey: string; isNew: boolean }>
```

**Definições exatas** (os testes conferem os textos, usando o hash falso `h = (s) => \`h(${s})\``):

- `normalizeText`: NFD → remove marcas combinantes (`\p{M}`) → minúsculas → troca qualquer espaço em branco (inclui U+00A0) por espaço comum → colapsa espaços → `trim`. A pontuação **fica**.
- `baseKeyInput(t)` = `JSON.stringify([t.source, t.accountRef, t.date, t.time ?? null, t.amount, normalizeText(t.description)])`.
- `identityKey(bk, n, hash)` = `hash(JSON.stringify([bk, n]))`.

### Casos de `normalizeText` e `baseKey`

| Caso | Esperado |
|---|---|
| `normalizeText('  PADARIA   São  João ')` | `'padaria sao joao'` |
| `normalizeText('CAFÉ Ação')` | `'cafe acao'` |
| `normalizeText('Padaria.')` vs `'Padaria'` | diferentes (pontuação conta) |
| `baseKeyInput(base)` | `'["manual","conta-1","2026-10-06",null,-830,"padaria exemplo"]'` |
| `baseKey(base, h)` | `'h(["manual","conta-1","2026-10-06",null,-830,"padaria exemplo"])'` |
| `amount` `-830` vs `-831` | `baseKey` diferente |
| diferença só de caixa, acento ou espaços na descrição | mesma `baseKey` |
| `time: '09:00'` vs sem `time` | `baseKey` diferente |
| `source`, `accountRef` ou `date` diferente | `baseKey` diferente |
| `externalId` diferente | mesma `baseKey` (o id da fonte não manda) |
| `status` `pending` vs `posted` | mesma `baseKey` (a efetivação não duplica) |
| `type`, `postedAt` ou `merchantName` diferente | mesma `baseKey` |
| `{ ...base, itemId: 'item-novo' } as NormalizedTransaction` | mesma `baseKey` (reconectar não duplica) |
| descrição com aspas e barra (`'Loja "X" \\ Y'`) | `baseKeyInput` continua JSON válido (`JSON.parse` devolve o array) |

### Casos de `assignIdentities`

`A`, `B`: transações com `baseKey` diferentes. `A'`: igual a `A`, mas com `externalId` diferente.

| Caso | Lote | `existingCounts` | Modo | Esperado (`occurrence` / `isNew`) |
|---|---|---|---|---|
| Lote vazio | `[]` | `{}` | os dois | `[]` |
| Determinismo | `[A]` em duas chamadas separadas | `{}` | `complete` | mesma `identityKey` |
| Dois cafés iguais, banco vazio | `[A, A]` | `{}` | `complete` | `1/novo`, `2/novo`; `identityKey` diferentes |
| **Reimportação integral** | `[A, A]` | `{A: 2}` | `complete` | `1/não`, `2/não` |
| **Período sobreposto** | `[A, A, A]` | `{A: 2}` | `complete` | `1/não`, `2/não`, `3/novo` |
| Mistura | `[A, B, A]` | `{A: 1}` | `complete` | `A1/não`, `B1/novo`, `A2/novo` |
| Id da fonte diferente | `[A']` | `{A: 1}` | `complete` | `1/não` (mesma identidade da linha gravada) |
| Reapresentação (apagou e recriou na fonte) | `[A]` | `{A: 1}` | `complete` | `1/não` |
| **Lote incremental** | `[A]` | `{A: 2}` | `incremental` | `3/novo` |
| Incremental misto | `[A, B, A]` | `{A: 2}` | `incremental` | `A3/novo`, `B1/novo`, `A4/novo` |
| Incremental, banco vazio | `[A, A]` | `{}` | `incremental` | `1/novo`, `2/novo` |
| Chave ausente no mapa vale 0 | `[B]` | `{A: 5}` | `complete` | `1/novo` |
| `identityKey` igual entre modos | `A` com `occurrence` 3 nos dois modos | | | mesma `identityKey` |
| Ordem e referência | qualquer lote | | | saída na mesma ordem; `saida[i].tx === lote[i]` |
| Sem mutação | lote, transações e mapa congelados (`Object.freeze`; o mapa embrulhado de forma que `set` lance) | | | não lança |
| `existingCounts` inválido (`-1`, `1.5`, `NaN`) | | | | lança `Error` (erro de programação, não regra de negócio) |
| `mode` inválido (`'x'` com cast) | | | | lança `Error` |
